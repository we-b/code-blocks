⏺ 設計観点からのコードレビュー

  1. 単一責任の原則（SRP）

  現状分析

  現在の TaskDuplicateService#duplicate が持つ責務を分解すると：

  TaskDuplicateService#duplicate
  ├── 1. 元タスクの取得 (findById)
  ├── 2. 名前の変換ロジック (title + "(コピー)")
  ├── 3. コピーする属性の決定 (content, genre, priority)
  ├── 4. リセットする属性の決定 (status → "todo")
  └── 5. 新タスクの永続化 (save)

  評価

  | 観点       | 評価  | コメント                                |
  |----------|-----|-------------------------------------|
  | 責務の集中度   | △   | 「複製」という大枠には収まっているが、複数の変換ルールが混在      |
  | 変更理由の単一性 | ×   | 「名前のルール変更」「コピー対象の変更」「保存方法の変更」が混在   |

  問題点

  2と3と4が同じメソッド内にハードコードされている

  // 現状: 3つの異なるルールが1箇所に混在
  duplicated.setTitle(original.getTitle() + "(コピー)");    // ← 名前変換ルール
  duplicated.setContent(original.getContent());             // ← コピールール
  duplicated.setGenre(original.getGenre());                 // ← コピールール
  duplicated.setPriority(original.getPriority());           // ← コピールール
  duplicated.setStatus("todo");                             // ← リセットルール

  2. 拡張性

  想定される将来の仕様変更

  1. 除外リストの追加: 「priority はコピーしない」
  2. 新属性の追加: Task に assignee が追加され、コピー対象にする
  3. 名前ルールの変更: 「(コピー)」→「_copy」に変更

  現状の拡張性評価

  | 変更シナリオ   | 現状の対応    | 影響範囲             |
  |----------|----------|------------------|
  | 除外属性の追加  | コード直接修正  | duplicate メソッド全体 |
  | 新属性の追加   | コード直接修正  | duplicate メソッド全体 |
  | 名前ルール変更  | コード直接修正  | duplicate メソッド   |

  結論: 拡張性は低い — どの変更も duplicate メソッドの直接修正が必要

  ---
  3. 改善案

  案A: シンプルな改善（定数による設定の外出し）

  import org.springframework.web.server.ResponseStatusException;
  import org.springframework.http.HttpStatus;

  @Service
  public class TaskDuplicateService {

      private static final String TITLE_SUFFIX = "(コピー)";
      private static final String INITIAL_STATUS = "todo";

      private final TaskRepository taskRepository;

      public TaskDuplicateService(TaskRepository taskRepository) {
          this.taskRepository = taskRepository;
      }

      public Task duplicate(Long taskId) {
          Task original = taskRepository.findById(taskId)
                  .orElseThrow(() -> new ResponseStatusException(
                      HttpStatus.NOT_FOUND, "Task not found"));

          Task duplicated = buildDuplicate(original);
          return taskRepository.save(duplicated);
      }

      private Task buildDuplicate(Task original) {
          Task duplicated = new Task();
          duplicated.setTitle(original.getTitle() + TITLE_SUFFIX);
          duplicated.setContent(original.getContent());
          duplicated.setGenre(original.getGenre());
          duplicated.setPriority(original.getPriority());
          duplicated.setStatus(INITIAL_STATUS);
          return duplicated;
      }
  }

  メリット: 変更時に定数やメソッドの修正箇所が明確
  デメリット: 条件付きコピーなど複雑なルールには対応しづらい

  ---
  案B: 柔軟な改善（コピー対象をリストで管理）

  @Service
  public class TaskDuplicateService {

      private static final String TITLE_SUFFIX = "(コピー)";
      private static final String INITIAL_STATUS = "todo";

      private final TaskRepository taskRepository;

      public TaskDuplicateService(TaskRepository taskRepository) {
          this.taskRepository = taskRepository;
      }

      public Task duplicate(Long taskId) {
          Task original = taskRepository.findById(taskId)
                  .orElseThrow(() -> new ResponseStatusException(
                      HttpStatus.NOT_FOUND, "Task not found"));

          Task duplicated = new Task();
          copyAttributes(original, duplicated);
          applySpecialRules(original, duplicated);
          return taskRepository.save(duplicated);
      }

      private void copyAttributes(Task original, Task duplicated) {
          duplicated.setContent(original.getContent());
          duplicated.setGenre(original.getGenre());
          duplicated.setPriority(original.getPriority());
      }

      private void applySpecialRules(Task original, Task duplicated) {
          duplicated.setTitle(original.getTitle() + TITLE_SUFFIX);
          duplicated.setStatus(INITIAL_STATUS);
      }
  }

  メリット: 「コピー対象」と「特別ルール」が明確に分離される
  デメリット: 小規模プロジェクトにはやや過剰

  4. 推奨

  | プロジェクト規模    | 推奨案 | 理由                   |
  |-------------|-----|----------------------|
  | 小〜中規模       | 案A  | 過度な抽象化を避けつつ、変更容易性を確保 |
  | 大規模・頻繁な仕様変更 | 案B  | 柔軟性が必要な場合に対応可能       |

  現在のプロジェクト規模であれば、案A が最もバランスが良いと考えます。
