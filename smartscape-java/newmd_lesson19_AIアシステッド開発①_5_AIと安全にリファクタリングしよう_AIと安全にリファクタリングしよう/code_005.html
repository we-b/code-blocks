リファクタリング案

---
案1: Service層の導入（@Service パターン）

ビジネスロジックを専用のServiceクラスに切り出す。

@Service
public class TaskService {
    private final TaskRepository taskRepository;

    public Task createTask(TaskCreateRequest request) {
        Task task = new Task();
        task.setTitle(request.getTitle());
        // ...
        return taskRepository.save(task);
    }
}

| メリット                     | デメリット            |
|---------------------------|-------------------|
| ビジネスロジックのテストが容易  | クラス数が増加        |
| 再利用可能（API、バッチ処理等） | シンプルなCRUDには過剰な場合も |
| Controllerが薄くなる        | 設計の一貫性が必要      |

---
案2: DTO（Data Transfer Object）パターン

リクエスト/レスポンスの変換を専用クラスに分離。

public class TaskResponse {
    private Long id;
    private String title;
    // ...

    public static TaskResponse from(Task task) {
        TaskResponse response = new TaskResponse();
        response.id = task.getId();
        // ...
        return response;
    }
}

| メリット                | デメリット            |
|-----------------------|-------------------|
| レスポンス組み立ての重複を解消 | 小規模アプリには冗長     |
| エンティティの内部構造を隠蔽   | マッピングコードが増える   |

---
案3: Bean Validation の活用

バリデーションをアノテーションで宣言的に定義。

public class TaskCreateRequest {
    @NotBlank(message = "タイトルは必須です")
    private String title;

    @Pattern(regexp = "todo|doing|done")
    private String status;
}

| メリット                | デメリット            |
|-----------------------|-------------------|
| バリデーションロジックの集約  | 複雑なルールには不向き   |
| 宣言的で読みやすい          | カスタムバリデーションが必要な場合も |

---
推奨: Service層の導入から始める

現在のコード規模を考慮すると、まずService層を導入し、
ControllerからビジネスロジックをServiceに移動するのが最もバランスが良いです。
